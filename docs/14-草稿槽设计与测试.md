## 一、为什么推翻 presence 重做

初版按**多人协同**设计：presence 三状态机（editing/idle/离线）+ 乐观锁。
真实场景是**个人笔记、单用户、多设备、无同时编辑**——presence 是为假想场景付的维护税。

教训：**设计服务于真实需求。先过度设计再砍，比一开始就想清楚成本高得多。**

## 二、草稿槽设计（最终定稿）

核心思想：**草稿和正文分离**。正文只在手动保存时变；编辑中的内容实时流进「草稿槽」。

### 存储：槽位覆写，不是追加表

```
documents 表加 3 个字段：
  draft_content      TEXT      -- 草稿内容
  draft_updated_at   DateTime  -- 最后一次同步时间
  draft_device       String    -- 哪台设备留下的
```

- **覆写式**：每次同步 UPDATE 同一行 → 每文档永远只有 1 份草稿，存储有界（1000 篇文档 = 最多 1000 个槽）
- **追加式**（WordPress revisions）：每次同步 INSERT 一行 → 一小时 1200 行，需要定时清理。我们要的是「最新未保存版」不是「每一版」，所以用槽位

### 三个时机各管各的（关键顿悟）

| 时机 | 规则 | 谁判断 |
|---|---|---|
| 同步（写进槽） | 打字停 2~3 秒就覆写（前端 debounce） | 无脑持续进行 |
| 可见（算不算草稿） | `now - draft_updated_at ≤ 10分钟` | 服务端**读取那一刻**惰性判断 |
| 清除 | 手动保存成功 → 置 NULL | 保存接口顺手干 |

「生成草稿的时机」这个问题不存在——草稿槽永远是最新的，10 分钟规则管的是**可见性**不是生成。

### 数据流

```
浏览器打字 → debounce 2~3s → WS 发 {type:"draft", content} → 覆写槽
正文保存（Ctrl+S）→ PUT /documents/{id}（乐观锁带 updated_at）→ 成功 → 清槽 → doc_saved 广播
其他设备打开 → GET /documents/{id} → has_draft + 草稿时间 + 设备名
查看草稿 → GET /documents/{id}/draft（过期 = 404，和「没有草稿」同语义）
```

## 四、踩坑：WS 里写库必须用依赖注入

**事故**：ws.py 里直接 `sessionLocal()` 建 session 写草稿，测试全挂。

**根因**：`sessionLocal` 绑定的是 `settings.database_url`（开发库 stella）。测试的 `dependency_overrides[get_db]` 只替换依赖注入路径，WS 手写 session 绕过了它 → 草稿写进开发库，测试读测试库，永远读不到。

**修复**：WS 端点也走 `db: Session = Depends(get_db)`——FastAPI 的 WebSocket 端点同样支持依赖注入，测试覆写机制自动生效。

教训：**任何地方拿 DB session 都走 get_db，不许手建**——否则测试覆写机制形同虚设。

## 六、面试可讲的点

1. 「为什么不用实时保存？」→ 保存语义与草稿语义分离：版本历史只对显式保存生效，草稿是易失的「正在输入」状态
2. 「为什么草稿用槽位覆写不用追加表？」→ 追加式存储无界、需清理任务；槽位式有界、零维护
3. 「10 分钟过期怎么实现的？」→ 惰性判断，读取时算，零后台任务
4. 「presence 为什么删了？」→ 真实场景单用户，草稿元信息（设备+时间戳）已能回答「谁在编辑」
