# Stella 服务器监控模块 — 方案设计

> 2026.8.13 定稿。本文是 M3 服务器监控模块（原「服务器状态面板」）的完整方案，范围从单机状态面板扩展为**分布式监控系统**（中心 + 多 agent 纳管）。
> 上游文档：`16-前端落地路线.md`（里程碑）、`17-前端M0-M1-外壳.md`（外壳）。

---

## 1. 需求与范围

### 1.1 定位

服务器监控模块 = Stella 的「网络/服务器运维面板」，三视图分离（看 / 做 / 管）：

| 视图 | 名称 | 本质 | 内容 |
|---|---|---|---|
| 总览 | 总览 | 被动「看」 | 服务器卡 + 服务监控卡 + 流量计数卡，模块化可添加 |
| 工具 | 工具 | 主动「做」 | ping / MTR / 下发命令 / 打流测速 |
| 服务器 | 服务器 | 资源「管」 | 本机 + 纳管服务器清单，进详情做设置 |

### 1.2 纳管范围（4 台）

- 2 × Linux（含 Stella 宿主 Nyarch 自己，也装 agent 统一纳管）
- 1 × Windows（1.8）
- 1 × 飞牛OS（NAS，按 Linux 处理）

### 1.3 明确不做（第一版）

- 交互式 Web Terminal（xterm.js + PTY）——先用命令执行框（B 方案），后续再上
- 告警通知（邮件等）——先占位列表栏，后面讨论
- 拖拽自由布局——先「预设类型 + 勾选添加」
- TimescaleDB / 降采样 / 数据清理——5s 裸存永久留，容量可承受（见 §4.3）
- **网盘（alist）接入**——导航先占位「网盘」入口，数据源抽象（本地 attachments + 网盘 WebDAV）留到图库那期一起做，不返工

## 2. 整体架构

### 2.1 架构形态

**轻量 Python agent + 推模式 + 纯 HTTP**（无 WebSocket、无独立心跳）：

```
┌─────────────┐   HTTP 轮询(5s)   ┌──────────────────┐
│  Stella 前端 │◄─────────────────►│   Stella 后端     │
│  (Vue3)     │                    │  (监控中心)       │
└─────────────┘                    │  ┌────────────┐  │
                                   │  │ PostgreSQL │  │ ← 历史数据落库
                                   │  └────────────┘  │
                                   └────────▲─────────┘
                                  agent POST 上报 / 拉配置
                          ┌─────────┴─────────┼──────────┐
                    ┌─────┴─────┐        ┌─────┴─────┐
                    │  agent A   │        │  agent B   │
                    │ (Linux)    │        │ (Windows)  │
                    └───────────┘        └───────────┘
```

### 2.2 核心简化决策

1. **数据上报 = 心跳**：agent 每 5s 上报一次流量，中心记录 `last_seen_at`，2 分钟无上报判 offline。上报动作不依赖流量大小（0 流量也照报），所以可靠。独立心跳字段删除。
2. **无 WebSocket**：前端 5s 轮询查最新点，实时延迟最多 5s，够用。
3. **中心也装 agent**：不搞「中心自纳管」特例——中心就是普通节点之一（agent 连 `localhost`），采集/上报/任务下发全走同一条路，没有 if-else 分支。
4. **去掉中心探测**：监控项一律挂 agent 节点探测，`node_id` 非空。中心不再有「探测者」身份——宿主机也装 agent 后，探测统一由 agent 执行；没有纳管节点就不让加监控项。
5. **监控项 agent 自探测 + 配置版本号**：监控项增删改在中心（唯一控制面），agent 靠 5s 心跳响应里的「配置版本号」感知变更，diff 后本地起/停/改探测定时器，探测结果主动上报。中心不搞后台调度器。
6. **PBR 绕过透明代理**：agent 以独立系统用户运行，透明代理按「源 UID」识别并打专属 mark，`ip rule` 最高优先级让 agent 全部流量（探测/打流/MTR/命令）直连真实公网出口，不被代理劫持。

## 4. agent 设计

### 4.1 安装

按平台给一键命令（中心「添加节点」入口生成）：

```bash
# Linux（含飞牛OS）
curl -sSL http://<stella>/api/agent/install.sh?token=<一次性> | sudo bash

# Windows（PowerShell 管理员）
iwr http://<stella>/api/agent/install.ps1?token=<一次性> -UseBasicParsing | iex
```

`<stella>` 公网 IP/域名在**设置里配置**（默认 `me.yaoyao.cfd` 之类）。一次性 token 用于注册，agent 用它换长期凭证，之后所有上报带凭证。

守护进程：Linux `systemd`；Windows 计划任务常驻。

**宿主机（Stella 宿主 Nyarch）**：首次进「服务器」页自动检测本机 OS 并生成「本机」条目（状态「未安装」），给「安装」按钮一键本地装（后端直接 exec），不用复制命令。远程节点仍走复制命令手动装。

**独立 UID + PBR**：install 时创建独立系统用户 `stella` 跑 agent；若宿主有透明代理（tun 模式），install 顺带配 PBR（§4.6），让 agent 探测/打流/MTR 走真实公网出口。

### 4.2 网卡检测与默认监控

```
注册时：
  1. 检测默认路由 → 出口网卡（多出口则全列出，metric 最低为主出口）
     Linux: /proc/net/route 找 Destination=00000000，Metric 最小
     Windows: Get-NetRoute -DestinationPrefix "0.0.0.0/0" 按 RouteMetric 排序
  2. 默认只监控主出口
  3. 枚举所有网卡 → 上报 interfaces 清单（含虚拟口 lo/docker0/veth/虚拟局域网）
  4. 虚拟口默认不采，用户在详情页勾选额外监控
```

### 4.3 采集与上报

| 数据类型 | 频率 | 端点 |
|---|---|---|
| 流量（rx_delta/tx_delta 按网卡） | 5s | `POST /api/agent/report` |
| 系统指标（cpu/mem/disk） | 60s | `POST /api/agent/report` |
| 配置拉取（监控网卡列表变更） | 60s | `GET /api/agent/config` |

**容量**（4 台、5s 颗粒、按网卡 ×2 张）：约 4.7 GB/年、9.4 GB/2 年。**不清理、不降采样、不分区**，PostgreSQL 单表几十 GB 内无压力。查询大范围时 SQL 动态聚合（`date_trunc`）再喂 echarts。

### 4.3b 脱管断档 → 内存队列补传（方案 ①）

**问题**：5s 上报，网络脱管时服务器正常但数据报不上来 → 历史流量图有缺口。脱管状态本身没问题（心跳超时 → `node_status_events` 记 offline），断的是时序数据（流量/CPU/内存）。

**方案 ①：agent 内存队列 + 断点续传**（老婆 8.14 拍板）：

```
agent 上报失败
   │
   ▼
数据压入内存队列（deque，按 ts 有序，环形上限防爆）
   │
   ▼ 恢复后
按时间顺序批量补传 → 中心按 ts 入库（天然有序）
```

- **为什么内存不落盘**：数据量极小（5s 一条，4 台每小时几千条，缓存几小时 < 1MB）。落盘是为了扛「agent 重启丢队列」，但「脱管 + agent 恰好重启」是极小概率 × 小损失，不值得写文件缓存。
- **队列上限**：环形队列，超上限丢最旧（防止 agent 长期脱管内存无限涨）。默认缓存上限 24h。
- **幂等**：两层兜底——① agent 侧「中心确认收到才出队」；② 中心侧 `(node_id, iface, ts)` 唯一约束 + `INSERT ... ON CONFLICT DO NOTHING`，重复自动丢弃。
- **补传顺序**：恢复后 agent 把积压队列按 ts 顺序一次批量 POST，中心按 ts 入库，前端历史图查询按 ts 排序无感。

> 边界：agent 进程挂掉期间的采集也停了（没采就没数据），这属于「agent 死了」，不是「脱管补传」能救的范畴——脱管补传救的是「网络断但 agent 活着」。

### 4.4 任务执行接口（工具页用）

agent 暴露给中心的执行接口（中心下发，agent 执行）：

- `POST /api/agent/exec` — 执行命令（B 方案），返回 stdout/stderr/exit_code
- `POST /api/agent/iperf3` — 起 iperf3 server（-s）或 client（-c），`-J` 输出 JSON
- `POST /api/agent/mtr` — 跑 mtr，输出逐跳
- `POST /api/agent/ping` — 跑 ping
- `POST /api/agent/speedtest` — 跑 speedtest（公共节点）

> 通信方向：agent **拉取/上报**为主（agent 主动连中心），任务执行也走「agent 轮询待办任务」而非中心反向连 agent——这样 agent 只需出站连接，兼容 NAT/防火墙。

### 4.5 监控项探测链路（agent 自探测，8.14 定稿）

监控探测统一由 agent 执行，中心只管配置（增删改）：

1. **配置下发**：agent 拉 `/agent/config`，中心返回该节点负责的监控项列表（id/type/target/interval/timeout）。
2. **版本号同步**：中心每次增/删/改监控项，`monitors_version` +1；agent 5s 心跳响应带版本号，变了就拉一次完整配置 diff。
3. **本地调度**：agent 维护每个监控项的定时器，到点按协议探测（ping/tcp/http/udp）。
4. **结果上报**：探测完 POST `/agent/monitor-check`，中心落 `monitor_checks` + 更新监控项 status/last_latency。

生效延迟 ≤ 5s（心跳周期）。agent 不自洽，永远听中心配置。结果上报复用 `(monitor_id, ts)` 幂等约束，补传/重试安全。

### 4.6 PBR — 绕过透明代理（8.14 定稿）

宿主有透明代理（tun2socks）时，agent 探测会被代理劫持（如 DNS 探测 0.9ms 假延迟）。方案：**以「源 UID」识别 agent 全部流量，最高优先级直连公网出口**。

- agent 以独立系统用户 `stella` 运行（install 创建）
- 透明代理规则链最前插：`-m owner --uid-owner stella -j MARK --set-mark <X>`
- `ip rule add fwmark <X> lookup main pref <最高>`（压过 tun 分流规则）

识别维度是「源」而非目标/协议/端口——agent 及其所有子进程（ping/iperf3/mtr/python socket/命令执行）同一 UID 全命中，加新功能无需再配。与 nyarch 现有防环（Xray mark=1→表100）同构。落地时读宿主现有 `ip rule` + mark 分配，定不冲突的 mark 值和压过 tun 的 pref。

## 5. 三个页面的模块清单

### 5.1 总览页

模块化卡片，预设 3 种类型 + 勾选添加（拖拽留后）：

| 卡片 | 显示 | 交互 |
|---|---|---|
| **服务器卡** | 一台机器：在线点 + hostname + CPU/内存/存储% | 点 → 跳服务器页该节点详情 |
| **服务监控卡** | 一组监控项网格：红绿点 + 延迟 + 丢包率 | 点 → 展开详情；添加监控项需选「探测节点」（agent），无节点不可添加 |
| **流量计数卡** | 某网卡：图标 + mini sparkline + 95值 + in/out + 总流量 | 点 → 展开大图 |

**流量计数卡字段**（用户定稿）：
- 图标（网卡/流量示意）
- **95 值**（95 分位速率，单位自适应 + 可手动切 Mbps/MB/s）
- in / out
- 该时间窗口总流量（自动换算 KB/MB/GB 更小单位）

### 5.2 工具页

| 工具 | 说明 |
|---|---|
| ping | 从中心或指定节点发起，返回延迟/丢包 |
| MTR | 从中心或指定节点到目标，逐跳延迟/丢包 |
| 下发命令 | B 方案：命令执行框，**入口醒目提示「可执行任意命令」** |
| 打流测速 | ① 自有服务器 iperf3 互打（选服务端+客户端+参数）② 公共 speedtest |

打流交互：
- iperf3 互打：选 server 节点 + client 节点 + 时长/并行/方向（正向 / `-R` 反向）
- 实时吞吐曲线：流式 append，结束定格不再重渲染，显示汇总（平均/峰值带宽）
- **并发限制：同一时间只允许一个打流任务**（前端排队/拒绝），防止打满带宽拖垮透明代理

### 5.3 服务器页

- 节点清单（本机 + 纳管服务器）：在线状态点、平台图标、hostname、最后心跳
- **宿主机「本机」条目**：首次进入自动检测 OS 生成，状态「未安装」给「安装」按钮一键本地装
- 添加节点表单：只填名称 + 平台（`Host` 字段移出，公网地址在「设置」全局配置）
- 点进详情：实时流量图 / 历史流量图 / 系统指标 / 网卡列表（勾选监控）/ 设置（重命名、移除=脱管）

## 6. 交互细节

### 6.1 流量图

- 视图分离：**实时**（滚动 60s，5s 刷新）/ **历史**（选时间范围）
- 时间范围预设：实时刷新 / 1天 / 7天 / 1周 / 上个月 / 自定义
- 时区：DB 存 UTC（timestamptz），前端按选时区渲染，默认 UTC+8，可切换
- 图表：echarts，自定义主题对齐 design token（暗夜蓝黑底 + 月白银线 + 樱粉高亮，面积图半透明渐变）

### 6.2 在线状态

- 节点三态：online / offline / removed
- 历史可用率：由 `node_status_events` 计算，总览可加「在线状态卡片」展示一个或多个服务器的历史/实时在线状态

### 6.3 告警（占位）

- 第一版不做，侧边栏/列表栏留「告警」占位，后续讨论

## 7. 风险与决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| agent 形态 | 轻量 Python 推模式 | 一条数据路径，无特例分支 |
| 存储 | 现有 PG 普通表 | 不引新组件，容量可承受 |
| 图表 | echarts | 功能全，主题对齐 token |
| 5s 落库 | 永久留、不清理 | 9.4GB/2年可承受；95 值需密集采样 |
| 心跳 | 数据上报即心跳 | 砍掉独立机制 |
| 实时推送 | HTTP 轮询 | 砍掉 WebSocket |
| 终端 | 命令执行框（B）先做 | 比交互式简单一个数量级 |
| 网卡监控 | 默认出口 + 手动加 | 自动判断默认路由 |
| 打流并发 | 限 1 个 | 防止打满带宽拖垮透明代理 |
| 脱管断档 | 内存队列补传（①） | 数据量小，覆盖「网断 agent 活」主场景，不落盘 |
| 网盘 | alist 先占位 | 数据源抽象留到图库那期，不返工 |
| 中心探测 | 去掉，统一 agent 探测 | 监控必须挂节点，宿主机也是 agent |
| 监控探测调度 | agent 自探测 + 配置版本号 | 中心无后台调度器，符合 push 模式 |
| Host 字段 | 移入「设置」全局公网地址 | 给 agent 安装命令 --url 用 |
| 宿主机纳管 | 自动检测 + 一键安装 | 本机特殊，可本地 exec 免复制命令 |
| PBR | 源 UID 识别 + 最高优先级直连 | 探测/打流/MTR 走真实公网出口 |
