## 一、项目定位（面试官的第一印象）

### 一句话

> 个人数字空间系统——在一个人用的系统里，刻意把真实业务中才会遇到的并发、安全、性能问题提前埋进去练。

### 30 秒版本（电梯演讲）

我做了一个全栈个人面板，前端 Vue3 + 后端 FastAPI + PostgreSQL。虽然用户只有我，但我刻意设计了乐观锁防并发覆盖、版本历史保证数据可恢复、FTS5 全文索引优化搜索、四层分层架构支持独立测试。这些设计让系统在任何规模下都能保证数据正确性。我能在面试时把每个设计决策的「为什么这样做」讲清楚。

### A、数据正确性（面试官最关心——你写的代码会不会丢数据）

| # | 真实业务场景 | Stella 实现 | 面试话术 | 状态 |
|---|-----------|-------------|---------|:--:|
| A1 | 两个客服同时编辑同一个客户备注，后保存的把先保存的盖掉了 | 乐观锁：保存时 `WHERE updated_at = 旧值`，不匹配返回 409 Conflict | 「为了防止并发编辑导致数据覆盖，我在文档表上用了乐观锁——保存时比对 `updated_at`，如果中间被人改过就拒绝写入并提示用户，而不是静默覆盖」 | ⬜ |
| A2 | 用户删了重要文档，想找回来——但没有任何历史记录 | `document_versions` 表：保存时自动生成 unified diff，前端展示高亮增减行，支持一键回退 | 「每次保存自动生成版本快照+ unified diff，用户可以看到每版改了什么，支持回退到任意版本」 | ⬜ |
| A3 | 用户网络卡顿，狂点保存按钮——同一条数据被写了三次 | 请求带幂等键（`idempotency_key`），数据库唯一约束拒绝重复写入 | 「用幂等键防止网络重试导致的重复写入——同一个操作无论发多少次，效果一样」 | ⬜ |
| A4 | 支付扣了钱但订单没生成——数据库事务失败导致不一致 | 关键操作包裹在 SQLAlchemy 事务里，要么全成功要么全回滚 | 「关联操作用数据库事务保证原子性——不会出现扣了钱但没生成订单的中间状态」 | ⬜ |

### B、性能（比你想象得早出现——数据量到万级就开始慢）

| # | 真实业务场景 | Stella 实现 | 面试话术 | 状态 |
|---|-----------|-------------|---------|:--:|
| B1 | 10 万条文档用 `LIKE '%keyword%'` 搜索要 3 秒，用户以为系统卡死了 | PostgreSQL FTS5 全文索引 + tsvector，毫秒级返回 | 「文档搜索从 LIKE 升级到 FTS5 全文索引——用倒排索引把搜索从秒级降到毫秒级」 | ⬜ |
| B2 | 列出 100 篇文档，每篇再单独查一次标签——101 条 SQL，数据库压力翻倍 | SQLAlchemy `joinedload()` 预加载关联数据，一条 JOIN 代替 N+1 次查询 | 「用 SQLAlchemy 的 joinedload 预加载消除 N+1 查询，把 101 条 SQL 降到 1 条」 | ⬜ |
| B3 | 文档树 5000 个节点一次性全部加载，前端卡了 10 秒 | 分页 + 懒加载：首次只加载顶层节点，展开目录才请求子节点 | 「树形结构用懒加载——首屏只渲染顶层，展开时按需加载，避免大响应体阻塞前端」 | ⬜ |
| B4 | 首页文档列表每次刷新都扫全表，数据库 CPU 飙升 | Redis 缓存首页结果，设置 TTL，写操作时主动失效缓存 | 「用 Redis 缓存热点数据——读多写少的场景下，缓存命中率 95%+，数据库查询量下降一个数量级」 | ⬜ |

### C、安全（不在简历第一行，但面试必问）

| # | 真实业务场景 | Stella 实现 | 面试话术 | 状态 |
|---|-----------|-------------|---------|:--:|
| C1 | 用户 A 把 URL 里的 `workspace_id` 改成 B 的——看到了别人的数据 | 资源归属校验：查询 workspace 或其下文档时，WHERE 条件必须带 `user_id` | 「所有 API 都校验资源归属——用户在 URL 里改别人的 workspace_id 也看不到数据」 | ⬜ |
| C2 | SQL 注入：`SELECT * WHERE title = '{用户输入}'` | SQLAlchemy 参数化查询，自动转义特殊字符 | 「SQLAlchemy ORM 默认参数化查询，不存在拼接 SQL 的风险」 | ✅ 已内置 |
| C3 | 恶意脚本疯狂调 API，带宽跑满，正常用户用不了 | slowapi 令牌桶限流：每 IP 每分钟最多 N 次请求 | 「用令牌桶算法实现接口限流——每个 IP 有固定配额，超过则返回 429，保护后端不被单个客户端耗尽」 | ⬜ |
| C4 | 路径穿越：`../../etc/passwd` 读到系统文件 | `os.path.realpath` 校验 + 路径白名单 | 「文件路径校验用真实路径比对，拒绝包含 `..` 或指向工作区外的路径」 | ✅ v1 已有 |

## 三、面试叙事：怎么一次讲清楚

### STAR 法模板

**Situation（情境）**
> 我之前做过一个 FastAPI 原型，但只有单文件 + 文件系统存储，功能跑通了但没法展示后端工程能力。我决定用 Vue3 + FastAPI + PostgreSQL 彻底重写，把它从「能跑的原型」升级成「可以放简历的作品」。

**Task（任务）**
> 我的目标是：在一个人用的系统里，主动把真实业务中才会遇到的并发、安全、性能问题提前设计进去——不是为了用而用，而是保证面试官问什么我都能讲出「为什么这样做」。

**Action（行动）**
> 后端四层分层（router→service→repository→DB）；文档保存用了乐观锁防并发覆盖；每次保存自动生成 unified diff 存版本历史；搜索从 LIKE 升级到 FTS5 全文索引；接口加了 slowapi 令牌桶限流；用 pytest 写了单元测试 + 集成测试 + 并发冲突测试；Docker Compose 一键部署。

**Result（结果）**
> 最后这个项目虽然是个人用的，但它的设计能抗住多用户并发、数据不会丢、搜索不会慢、出了问题有日志可追——我能在面试时把每个设计决策都讲清楚。

### 面试官的灵魂三问

| 面试官问 | 你的回答 |
|----------|---------|
| 「你这个项目就你一个人用，为什么做这么多？」 | 「正因为用户少，我可以把时间花在架构设计上而不是救火。这些设计不是过设计——如果我明天把系统开放给 100 个人用，代码不用改，只是加硬件。」 |
| 「乐观锁和悲观锁有什么区别，你为什么用乐观锁？」 | 「悲观锁加锁后别人读都读不了，适合金融扣款；乐观锁不锁读只锁写，适合协作编辑。Stella 是文档编辑场景，冲突概率低，乐观锁更合适。」 |
| 「你为什么选 PostgreSQL 而不是 MySQL？」 | 「PostgreSQL 的 JSONB 对文档元数据很友好，全文搜索用 tsvector 也比 MySQL 的 FULLTEXT 成熟。而且 PG 的隔离级别默认更严格，数据不容易丢。」 |

## 四、测试策略

```
第一层：单元测试（service 层纯函数）
  → 测业务逻辑，不连数据库，毫秒级跑完
  → 例：版本 diff 计算、frontmatter 解析

第二层：集成测试（TestClient + 测试 DB）
  → 测 API 行为 + 数据库写入 + 乐观锁冲突
  → 例：创建文档→断言 status 201→验证数据库真有这条

第三层：边界/异常测试
  → 测「什么时候该报错」
  → 例：标题超 500 字 → 422、并发保存 → 409、workspace 不存在 → 404
```

### 优先实现顺序

1. `tests/conftest.py` — 测试 DB + TestClient fixture ← **今天**
2. `tests/test_workspaces.py` — 最简 CRUD 测试，先把测试框架跑通
3. `tests/test_documents.py` — 文档 CRUD + 乐观锁并发测试 ⭐ 面试价值最高
4. `tests/test_versions.py` — 版本历史 + diff + 回退
5. 越权校验实装 + 测试
6. N+1 查询优化 + 对比测试（证明优化有效）
7. Locust 压测脚本

## 五、真实业务对照（应对后续面试的「遇到过什么线上问题」）

以下不是 Stella 目前会遇到的，而是**面试官可能问的「你遇到过什么线上问题」**——提前知道答案：

| 线上问题 | 怎么应对 | Stella 能映射到的设计 |
|---------|---------|---------------------|
| 数据库连接池耗尽 | 设置合理的 pool_size + 超时 + 监控连接数 | SQLAlchemy engine 连接池配置 |
| 慢查询把数据库拖死 | slow query log → EXPLAIN ANALYZE 定位 → 加索引 | B1：FTS5 索引优化 |
| 缓存雪崩（大量缓存同时过期） | TTL 加随机抖动 + 预热缓存 | B4：Redis 缓存策略 |
| 接口被恶意刷 | 限流 + IP 黑名单 + WAF | C3：slowapi 令牌桶 |
| 发布后 API 返回格式变了，前端挂 | 接口版本号（/api/v1/） + 向后兼容 | Stella 目前不需要，但面试时可提「项目初期加了 `/api/v1/` 前缀预留版本空间」 |
| 数据库磁盘满了 | 监控磁盘使用率 + 定期清理日志 | D5：结构化日志 + 日志轮转 |
| 用户说「我点了保存结果没存上」 | 请求日志 + 幂等键 → 回溯到具体请求 | A3 + D5 |
