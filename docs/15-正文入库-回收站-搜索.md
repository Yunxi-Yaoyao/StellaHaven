# 15 - 正文入库 · 回收站 · 全文搜索

> 2026-08-09 · 后端功能收官三件套。至此 Stella 笔记后端功能定型。

## 一、正文进 DB（③）

**决策**：弃「笔记=磁盘文件」的 Obsidian 思路，正文存 `documents.content`（TEXT）。
`file_path` 退化为纯逻辑路径（展示用），草稿正文都在 DB，一条命。

**content_hash 服务端权威**：传了 content 服务端就重算 sha256，不信前端算的——
前端算的可能和实际存的不一致，hash 的意义是「内容变没变」的可靠判据。

```python
if data.content is not None:
    data.content_hash = sha256(data.content.encode()).hexdigest()
```

## 二、回收站（④）

- `deleted_at` 字段：NULL = 正常，有值 = 在回收站
- **两级删除**：DELETE 正常文档 → 软删；DELETE 回收站里的 → 物理删
- 正常列表/搜索/GET 都过滤 `deleted_at IS NULL`
- **惰性过期清理**：没有定时任务——任何人访问回收站时，顺手物理清掉超过 30 天的
  （和草稿的 10 分钟惰性判断同一个哲学：**清理动作寄生在读操作上**）
- 还原：`POST /documents/{id}/restore`

## 三、全文搜索（②）

**为什么 pg_trgm 不用 tsvector**：PG 原生 tsvector 按空格/标点分词，
中文整句连写（「今天晚饭吃了青椒肉丝面」）会被当成**一个超长词**，
搜「青椒肉丝」永远miss。pg_trgm 把文本切成三字元滑动窗口切片，
中文任意子串都能命中，GIN 索引让 `ILIKE '%kw%'` 走索引而不是全表扫。

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX ... ON documents USING gin (title gin_trgm_ops);
CREATE INDEX ... ON documents USING gin (content gin_trgm_ops);
```

端点：`GET /documents/search?q=关键词&workspace_id=...`
范围：标题 + 正文，不含回收站，限定 workspace。

## 四、FastAPI 路由顺序坑

`/search`、`/trash` 这种**固定路径必须声明在 `/{doc_id}` 之前**。
Starlette 按声明顺序匹配，`/documents/search` 先撞上 `/{doc_id}` 的话，
"search" 会被拿去解析 UUID → 422。血的顺序：

```python
@router.get("/search")   # 固定路径先声明
@router.get("/trash")
@router.get("/{doc_id}") # 动态路径后声明
```

## 六、面试话术

- 「软删除还是物理删除？」→ 两级：先进回收站（软删标记），回收站里再删才物理清；过期惰性清理，无后台任务
- 「中文全文检索怎么做？」→ tsvector 分词对中文失效，pg_trgm 三字元 + GIN 索引
- 「content_hash 谁算？」→ 服务端权威，防止前后端不一致导致脏判
